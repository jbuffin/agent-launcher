# 5. One session per task, conversation ID fixed at launch

Status: accepted

## Context

Reopening a task must not create a second primary session, and a resumed agent needs its conversation ID. Finding the ID after launch means scraping the agent's files or screen.

## Decision

A task has one `sessions` row for life; the registry refuses a second. Reopen, resume and restart update that row's `terminal_sessions` (and, for restart, `agent_conversations`) in place. The conversation ID is generated by the launcher and given to the agent at launch where the agent allows it (Claude Code 2.1.295: `--session-id <uuid>`; resume with `--resume <id>`, both read from `claude --help`). Agents that do not are not resumable. An agent is treated as exited only on positive evidence from its adapter; otherwise the workspace is focused.

## Consequences

No ID discovery. A conversation that never received a message has nothing to resume (Claude Code says so), and the answer is `restart`. Restoration is reported only when the agent adapter has a pattern that confirms it; until one is observed live the outcome is "resume attempted, not confirmed".

Databases written before this ticket could hold several sessions for one task; the latest is treated as the primary one. Terminal ownership (`created_by_launcher`) is persisted from this ticket on (state migration 3); earlier rows count as not owned and are never force-closed.
